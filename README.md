# Credit Risk Prediction — Explainable ML with Deployment

Predicts whether a loan applicant is likely to default, using the [Statlog German Credit Data](https://archive.ics.uci.edu/dataset/144/statlog+german+credit+data) from the UCI Machine Learning Repository — 1,000 real loan applicants with 20 demographic, financial, and credit-history features.

**Live demo:** [add your Streamlit Cloud link here after deploying]

## Why this project

Most portfolio ML projects stop at "I trained a model and got X% accuracy." This one covers the parts of the pipeline that actually matter in a lending context:

- **Handles a real business cost asymmetry.** Missing an actual defaulter is far more expensive for a bank than rejecting a good applicant — the UCI dataset's own cost matrix weights this 5:1. The notebook tunes the decision threshold around that trade-off instead of defaulting to 0.5.
- **Explains every prediction with SHAP**, not just the model's overall behavior. In lending, "the model said so" isn't good enough — you need to be able to point to *why* someone was flagged as risky, both for internal review and (increasingly) for regulatory reasons.
- **Is deployed**, not just a notebook. A Streamlit app takes a new applicant's details and returns a risk score with a live SHAP explanation.
- **Reports honest numbers.** ROC-AUC of ~0.75 on this dataset — a real, credible score for 1,000 noisy real-world records, not an inflated claim.

## Approach

1. **Data cleaning** — mapped the UCI dataset's coded attribute values (e.g. `A11`, `A34`) to human-readable labels.
2. **EDA** — checked class balance (70% good / 30% bad — imbalanced, not extreme), and validated that the raw data shows sensible patterns (larger/longer loans skew riskier) before trusting any model output.
3. **Feature engineering** — added `credit_amount_per_month` (loan size relative to repayment speed) and an `age_bucket`, one-hot encoded the rest.
4. **Class imbalance** — handled with SMOTE on the training set only, never the test set.
5. **Modeling** — Logistic Regression as an interpretable baseline, XGBoost as the main model to capture non-linear feature interactions.
6. **Threshold tuning** — optimized the decision cutoff for the minority (default) class rather than using the default 0.5, since a missed defaulter costs more than a wrongly rejected good applicant.
7. **Explainability** — SHAP summary plots (which features matter overall) and per-applicant force plots (why *this* applicant got *this* score).
8. **Deployment** — Streamlit app that takes new applicant inputs and returns a live prediction with a SHAP breakdown.

## Results

| Model | ROC-AUC |
|---|---|
| Logistic Regression (baseline) | ~0.75 |
| XGBoost | ~0.75 |

Both models land in a similar, honest range for this dataset size — XGBoost's main advantage here is that it captures feature interactions Logistic Regression can't, which shows up in the SHAP analysis rather than in a large accuracy gap.

**Top risk drivers (from SHAP):** checking account status, loan duration, savings account balance, and credit amount relative to loan duration — all of which line up with how a credit analyst would actually reason about risk.

## What I'd improve with more time

- Compare against LightGBM and CatBoost for training-speed and small accuracy gains.
- Add macroeconomic context (unemployment rate, interest rates at time of application) as features.
- Validate the threshold against an actual bank's cost figures instead of a generic F1-optimal point.
- Move from SMOTE to class-weighted loss and compare — SMOTE synthesizes data, which isn't always preferable to just re-weighting.
